# 开发笔记

写给接手这个项目的人。这里只记**从代码里看不出来**的东西：为什么这么做、踩过哪些坑、哪些地方还欠着。
怎么运行、目录结构、图集格式见 [README](../README.md)。

## 1. 项目的边界

- **是同类玩法的原创游戏，不是某款老游戏的复刻。** 起因是想重现「没有等级、武功靠用出来」的经典武侠网游体验，但名字、地图、NPC、怪物、界面、美术全部是新做的。往后加内容也守这条线：可以借鉴玩法机制，不照搬具体作品的名称与形象。
- **运行时不做 3D。** 需求方明确不要 3D 游戏（实时 3D 不如 2D 贴图精致，且吃性能），所以 three.js 只出现在 `tools/bake/` 的离线烘焙里，`src/` 里不允许引入。
- **只做单机 demo**，不联网。目标是在浏览器里体现玩法与画面，不是完整游戏。
- 全部素材都由仓库里的代码程序化生成，没有任何第三方美术或音频文件；界面字体用系统自带的宋体 / 楷体。

## 2. 美术方向是怎么定下来的

人物改过三版，前两版都被否了。README 里的「美术方向」是结论，这里是过程，避免重蹈覆辙：

| 版本 | 做法 | 被否的原因 |
|---|---|---|
| 一 | 胶囊、球体拼成的刚体分节人偶，头大身短 | 「Q 版」「像木偶，不像真人」 |
| 二 | 八头身蒙皮躯体，白衣渐染长袍、玉冠、披肩长发 | 「偏仙侠而非武侠」「美男娘炮」，且发际线太高像秃顶 |
| 三（现行） | 斗笠、粗布短褐、敞襟赤臂、缠臂绑腿、布鞋、酒葫芦，宽肩厚胸 | — |

从中得到的经验：

- **验收的人会把图集放大到好几倍看**，不只是看游戏里 90 像素高的小人。所以「反正游戏里看不清」不成立，手、脚、发际线这些都要经得起放大。
- 「木偶感」主要来自三件事：肢体是分开的刚体段、表面是没有起伏的圆柱、材质是没有纹理的纯色。对应的解法是蒙皮连续曲面、按肌肉走向调截面环、给布料和皮肤画明暗贴图。
- 45° 俯视下**头顶是最显眼的部位**。头发和脸很难做好，斗笠直接把问题盖住，还成了角色标志。
- 四足动物经历了同样的过程（刚体分节 → 蒙皮），现在仍是全项目里最弱的美术，见第 7 节。

## 3. 素材管线为什么长这样

**为什么用 three.js + 无头 Chrome 而不是 Blender**：开发机上没有 Blender，而游戏本身就是 TypeScript，用同一种语言写建模和烘焙，迭代最快。代价是模型全靠代码堆，没有美术工具可用。

**天空遮蔽是用很多盏平行光累积出来的**（`core.ts`）。每帧从上半球取几十个方向，各渲染一次带阴影的漫反射再求平均，等价于「均匀天空 + 遮挡」。这样褶皱、腋下、帽檐下自然变暗，不依赖后处理 SSAO。灯光强度在启动时用一块白板标定，不依赖 three.js 的光照单位约定（它在历史版本里变过）。

**太阳方位是固定的。** 地面投影在烘焙时就画死了（阴影图集的 R 通道），所以运行时昼夜只改光的颜色和强度，不改方向。想让影子随时间转动，得改成运行时投影，是一次大改。

**法线存视空间、另存一个高度通道**，是整个渲染器的基础：
- 视空间法线的 z 恒为正，可以只存 x、y，省出通道放高度。
- 有了每个像素的离地高度，就能还原它的世界坐标，于是点光源衰减、逐像素深度遮挡（人走进牌坊、站在桥栏杆之间）都不需要手工排序。
- 同一屏幕像素上，沿视线越靠近镜头的点世界 z 越大，所以**深度直接用世界 z**，不用算真正的视线距离。

**颜色是「线性空间预乘 alpha 后再做 sRGB 编码」。** 这个不直观的格式是被逼出来的：直通 alpha 需要在透明像素下面垫颜色才能正确过滤，但有损 WebP 会把透明像素的 RGB 清零；在 sRGB 空间预乘又会让边缘发黑。现行做法下，按 sRGB 纹理采样出来的就是预乘的线性颜色，过滤、mipmap、有损压缩三者都对。

**法线图的 alpha 存的是「1 − 光泽」而不是光泽。** 这样没有 alpha 通道的旧图读出来就是光泽 0，不用全部重烘。光泽上限钳在 0.97，是为了不让 alpha 变成 0——那样编码器会把这个像素的法线当成透明区域清掉。

**压缩质量不能随便调**：颜色用有损（90），法线用近无损，阴影用有损（82）。法线没有用有损，是担心色度抽样让存在 R、G 里的 x、y 分量互相串扰——这是推断，没有实测对比过；法线图占了素材体积的大头，想压体积可以从这里验证。

## 4. 踩过的坑

### 烘焙

- **`sharp` 的 `png({ effort })` 会悄悄开启调色板量化**，把图压成 256 色，法线和高度全毁，而且肉眼不容易发现（只是光照显得脏）。现在已改用 WebP；如果再输出 PNG，必须写 `palette: false`。
- **烘焙时改源码会让任务从头再来。** Vite 检测到文件变化会整页重载，而烘焙页的状态全在内存里。现在 `bake.mjs` 关掉了热更新和文件监听，副作用是：**一次烘焙启动后，中途改的代码不会生效**，要等下一次运行。
- **不要同时跑多个烘焙或截图。** 它们抢同一块 GPU，单个任务会从一分钟拖到三分钟。全量重烘约 15–20 分钟。
- 图集打包器要选**最接近正方形**的布局。早期只按面积选，会得到 768×7600 这种超出纹理上限的长条。
- **带缩放的蒙皮网格，绑定前必须先更新世界矩阵**（`humanoid.ts` 的 `skin()`）。否则骨骼逆矩阵和绑定矩阵不在同一空间，缩放不为 1 的角色（村童）会整个扭曲，而其他角色完全正常。
- 蒙皮网格的包围盒要每帧重算，否则裁剪框按绑定姿势来，挥出去的武器会被切掉。
- 宽而扁的飘带用 `Ribbon`（质点链 + 扁管）会拧成锯齿状，围巾这类宽布条要用 `Cloth`（质点网格）。`Ribbon` 只适合发丝、细带。
- 长袍下摆是三片布。片与片之间如果正好对缝，胯部会露出一个黑三角，所以前两片要压住后片一截、半径略大几毫米。
- 布料的「迎面风」（`anims.ts` 里各动画的 `wind`）调大了头发和衣摆会被吹成水平线，现在的 9 是试出来的。

### 运行时

- **阴影曾经「看不见」，其实是对比度不够。** 色调映射加伽马会把明暗比压掉一大半，物理上正确的环境光会显得影子很淡。现在白天的环境光是故意压低、阳光故意调高的（`fx.ts` 的 `KEYS`）。
- 白衣角色站在浅色石板上会融进背景。现在光照着色器里有一道「轮廓暗边」：比邻近像素矮的一侧略压暗。它对所有物体生效，是画面有「描边感」的来源。
- 树冠会把人完全挡住，所以人物走到高大物件后方时该物件会淡出（`world.ts` 的 `tall` / `fade`）。
- 镜头最大只放到 1.3 倍，因为人物是按每米 128 像素烘的，再放大就糊。想要更大的特写得提高烘焙分辨率，图集体积按平方涨。
- 异步加载纹理时，`await` 之后 GL 的绑定状态可能已经被别的加载改掉。上传纹理的 GL 调用要放在同一段同步代码里（`assets.ts`）。
- 野外怪物的图集是进游戏后在后台加载的（`main.ts` 的 `DEFERRED`），否则首屏要等十几秒。加一种怪记得放对列表，并确认刷怪逻辑能在图集晚到时补刷。

### 地图

- **桥曾经没搭到对岸，整个河东都走不过去**，截图上还看不出来。之后加了 `tools/map/check-map.mjs`，改完地图一定要跑。现在河道在桥位处是特意收窄、岸线取直的。
- 地图生成是带固定种子的伪随机，改动摆放逻辑里**任何一处**随机数的调用次数，后面所有树和石头的位置都会变。
- 碰撞与灯光不写在地图文件里，而是运行时从图集 json 的 `info` 读（`solid`、`lights`、`deck`、`walk`、`fires`、`door`）。好处是重烘建筑后碰撞自动跟上；代价是这套字段没有类型约束，改名要全局搜。

## 5. 怎么验证改动

没有自动化测试，靠的是「无头浏览器里真跑 + 截图用眼看」：

- **`tools/shot.mjs`** 会起一个开发服务器，在无头 Chrome 里打开游戏并截图。配合 `--eval` 可以直接驱动游戏对象（页面上暴露了 `window.game`），例如把角色传到某处、选中最近的敌人打十秒、再把修为和背包读回来。这是目前唯一的回归手段。
- 地址栏参数：`autostart`（跳过标题画面）、`nosave`（清存档）、`x` / `z`（出生位置）、`hour`（时辰）、`zoom`。
- `window.game.r.debug = 1 / 2 / 3` 分别显示阴影遮罩、反照率、法线高度缓冲，排查光照问题时很有用。
- 模型改完先出预览再烘：`pnpm bake <任务> --preview --filter='正则' --ppu=400`。`--ppu` 调高能看清细节，**一定要放大看**（见第 2 节）。
- 烘焙和截图都依赖本机的 Chrome，路径不在默认位置时用环境变量 `CHROME_PATH` 指定。

## 6. 数值上的意图

数值没有经过完整通关的校准，只保证了方向正确：

- 修为增长：越高越慢，且**对手的品阶远低于自己时几乎不涨**。这是玩法的核心，木人桩因此只适合入门。
- 现实约 5 分半钟长一岁，一个昼夜约 15 分钟。都是为了 demo 压缩过的。
- 1 级角色进黑风寨会在几秒内被打死，这是有意的；但中后期的难度曲线（尤其是寨主战）没人实际打过。

## 7. 还欠着的

- **音效和配乐没有人听过。** 它们是程序合成的，开发全程在无头环境里，只确认了不报错。
- **没有人手动完整通关过**，八段主线只用脚本逐段验证了流程。
- 动物仍然偏简化：腿根与躯干有折痕，倒地是整体侧翻；鸡和木人桩还是刚体。
- 所有精灵都是静态的，树和草不会随风动。
- 贴图显存估算在 1GB 上下，只在一台 Apple M4 上跑过，没有做低配适配，也没有移动端和触屏支持。
- 图集（约 100MB）直接提交在仓库里，方便克隆即玩，但每次重烘都会让仓库变大。素材稳定后可以考虑挪到 Git LFS 或发布产物里。
